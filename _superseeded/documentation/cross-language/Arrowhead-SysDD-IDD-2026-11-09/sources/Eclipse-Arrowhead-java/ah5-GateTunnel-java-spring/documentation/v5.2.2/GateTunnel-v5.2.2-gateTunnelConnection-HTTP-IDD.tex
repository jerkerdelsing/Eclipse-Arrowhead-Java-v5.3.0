\section{Overview}
\label{sec:overview}

This document describes the \texttt{gate\allowbreak{}Tunnel\allowbreak{}Connection} service interface of the GateTunnel system, which provides relay sessions between the local cloud and a neighbour cloud: provider and consumer sessions opened by the Gatekeeper, and the legacy control sessions.

It's implemented using protocol, encoding as stated in below table:
\begin{table}[ht!]
  \centering
  \begin{tabular}{|l|l|l|}
    \hline
    \rowcolor{gray!33} Profile type & Type & Version \\ \hline
    Transfer protocol & HTTP & 1.1 \cite{rfc9112} \\ \hline
    Data encryption & TLS & 1.3 \cite{rfc8446}, 1.2 \cite{rfc5246} \\ \hline
    Encoding & JSON & RFC 8259 \cite{rfc8259} \\ \hline
    Compression & N/A & - \\ \hline
    Semantics & N/A & - \\ \hline
    Ontology & N/A & - \\ \hline
  \end{tabular}
  \caption{Communication and semantics details used for the \texttt{gate\allowbreak{}Tunnel\allowbreak{}Connection} service interface}
  \label{tab:comunication_semantics_profile}
\end{table}

This document provides the Interface Design Description IDD to the \textit{gateTunnelConnection -- Service Description} document \cite{gt-gateTunnelConnection-sd}.
For further details about how this service is meant to be used, please consult that document.

The rest of this document describes how to realize the \texttt{gate\allowbreak{}Tunnel\allowbreak{}Connection} service
interface in detail. Both in terms of its operations (Section \ref{sec:operations}) and its information model (Section \ref{sec:model}).

\subsection{Interface registration}

The service is registered in the ServiceRegistry with the interface template \texttt{generic\_\allowbreak{}https}, policy \texttt{CERT\_\allowbreak{}AUTH}, access address \texttt{gatetunnel}, port 8453 and base path \texttt{/\allowbreak{}gatetunnel}. The \texttt{operations} property of the interface lists the operations below with their method and path relative to the base path (path parameters are placeholders such as \texttt{\{id\}} that the consumer fills in):

\noindent\begin{longtable}{| p{5.2cm} | p{1.6cm} | p{8.4cm} |} \hline
\rowcolor{gray!33} Operation & Method & Path \\ \hline \endhead
\texttt{connect-\allowbreak{}provider} & POST & \texttt{/\allowbreak{}connect\_\allowbreak{}provider} \\ \hline
\texttt{connect-\allowbreak{}consumer} & POST & \texttt{/\allowbreak{}connect\_\allowbreak{}consumer} \\ \hline
\texttt{close-\allowbreak{}sessions} & POST & \texttt{/\allowbreak{}close\_\allowbreak{}sessions} \\ \hline
\texttt{open-\allowbreak{}provider-\allowbreak{}session} & POST & \texttt{/\allowbreak{}intercloud/\allowbreak{}provider} \\ \hline
\texttt{open-\allowbreak{}consumer-\allowbreak{}session} & POST & \texttt{/\allowbreak{}intercloud/\allowbreak{}consumer} \\ \hline
\end{longtable}

\section{Service Operations}
\label{sec:operations}

The interfaces of the \texttt{gate\allowbreak{}Tunnel\allowbreak{}Connection} service, its operations, data models and implementation are provided below.
In particular, each subsection first names the HTTP method and path used to call the operation, after which it names the abstract operation from the \texttt{gate\allowbreak{}Tunnel\allowbreak{}Connection} SD document, as well as input and output types.

Every request needs mutual TLS with a system or operator certificate of the cloud and \texttt{Authorization: Bearer IDENTITY-TOKEN//<token>}; the token is verified with Authentication and must belong to the system named by the certificate. Request and response bodies are \texttt{application/json} unless stated otherwise.
Errors are answered with \texttt{\{\"error\": \"<text>\"\}} and the status codes \texttt{400 Bad Request} (invalid input), \texttt{401 Unauthorized} (no valid identity), \texttt{403 Forbidden} (caller not permitted), \texttt{404 Not Found}, \texttt{500 Internal Server Error}, \texttt{502 Bad Gateway} (a system it depends on failed) and \texttt{503 Service Unavailable} (overloaded).

\osubsection{connect-provider}{POST}{/\allowbreak{}gatetunnel/\allowbreak{}connect\_provider}{\mref{ControlSessionRequest}}{\mref{ControlSessionResult}}

Creates a legacy control session for a provider (v4 API).

A successful call returns \texttt{201 Created} with the output in the body.

\begin{lstlisting}[label={lst:connect-provider},caption={An \oref{connect-provider} invocation.}]
POST /gatetunnel/connect_provider HTTP/1.1
Host: gatetunnel:8453
Authorization: Bearer IDENTITY-TOKEN//<token>
Content-Type: application/json

{
  "providerCloud": "GoCloud|Company",
  "serviceDefinition": "temperatureReading",
  "queueId": "gatetunnel.7f3c2a10",
  "peerName": "GateTunnel-7f3c2a10"
}
\end{lstlisting}

\begin{lstlisting}[label={lst:connect-provider-resp},caption={An \oref{connect-provider} response.}]
{
  "sessionId": "7f3c2a10",
  "queueId": "gatetunnel.7f3c2a10",
  "peerName": "GateTunnel-7f3c2a10",
  "serverPort": 8000,
  "state": "PROVIDER_READY"
}
\end{lstlisting}

\osubsection{close-sessions}{POST}{/\allowbreak{}gatetunnel/\allowbreak{}close\_sessions}{\mref{ClosePortsRequest}}{\pref{Array}$<$\allowbreak{}\pref{Object}$>$}

\section{Data Models}
\label{sec:model}

Here, all data objects that can be part of the service calls associated with this service are listed in alphabetic order.
Note that each subsection, which describes one type of object, begins with the \textit{struct} keyword, which is meant to denote a JSON \pref{Object} that must contain certain fields, or names, with values conforming to explicitly named types.
Fields that are not needed may be omitted or \texttt{null} in requests; empty fields are omitted in responses.
As a complement to the primary types defined in this section, there is also a list of secondary types in Section \ref{sec:model:primitives}, which are used to represent things like hashes, identifiers and texts.

\subsection{Primitives}
\label{sec:model:primitives}

Note that the official standard is defined in terms of parsing rules, while this list only concerns syntactic information.
Furthermore, the \pref{Object} and \pref{Array} types are given optional generic type parameters, which are used in this document to signify when pair values or elements are expected to conform to certain types.

\noindent\begin{tabularx}{\textwidth}{| p{4.6cm} | X |} \hline
\rowcolor{gray!33} Type & Description \\ \hline
\pdef{Array} & A JSON Array \cite{rfc8259}; \pref{Array}$<$A$>$ has elements of type A. \\ \hline
\pdef{Number} & JSON Number, an integer. \\ \hline
\pdef{Object} & JSON Object; \pref{Object}$<$A$>$ has string keys and values of type A. \\ \hline
\pdef{String} & JSON String. \\ \hline
\end{tabularx}
