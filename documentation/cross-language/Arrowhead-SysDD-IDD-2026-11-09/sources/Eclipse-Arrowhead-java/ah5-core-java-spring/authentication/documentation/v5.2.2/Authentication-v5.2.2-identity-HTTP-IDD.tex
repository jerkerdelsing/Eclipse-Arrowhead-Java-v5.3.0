\section{Overview}
\label{sec:overview}

This document describes the \texttt{identity} service interface of the Authentication system, which provides authentication of systems: a system logs in with its credentials and obtains an identity token, which it presents to other systems; providers verify such tokens.

It's implemented using protocol, encoding as stated in below table:
\begin{table}[ht!]
  \centering
  \begin{tabular}{|l|l|l|}
    \hline
    \rowcolor{gray!33} Profile type & Type & Version \\ \hline
    Transfer protocol & HTTP & 1.1 \cite{rfc9112} \\ \hline
    Data encryption & TLS & 1.3 \cite{rfc8446}, 1.2 \cite{rfc5246} \\ \hline
    Encoding & JSON & RFC 8259 \cite{rfc8259} \\ \hline
    Compression & N/A & - \\ \hline
    Semantics & N/A & - \\ \hline
    Ontology & N/A & - \\ \hline
  \end{tabular}
  \caption{Communication and semantics details used for the \texttt{identity} service interface}
  \label{tab:comunication_semantics_profile}
\end{table}

This document provides the Interface Design Description IDD to the \textit{identity -- Service Description} document \cite{auth-identity-sd}.
For further details about how this service is meant to be used, please consult that document.

The rest of this document describes how to realize the \texttt{identity} service
interface in detail. Both in terms of its operations (Section \ref{sec:operations}) and its information model (Section \ref{sec:model}).

\subsection{Interface registration}

The service is registered in the ServiceRegistry with the interface template \texttt{generic\_\allowbreak{}https} (\texttt{generic\_\allowbreak{}http} when TLS is disabled), access port 8444 and base path \texttt{/\allowbreak{}authentication/\allowbreak{}identity}. The \texttt{operations} property of the interface lists the operations below with their method and path relative to the base path (path parameters are placeholders such as \texttt{\{id\}} that the consumer fills in):

\noindent\begin{longtable}{| p{5.2cm} | p{1.6cm} | p{8.4cm} |} \hline
\rowcolor{gray!33} Operation & Method & Path \\ \hline \endhead
\texttt{identity-\allowbreak{}login} & POST & \texttt{/\allowbreak{}login} \\ \hline
\texttt{identity-\allowbreak{}logout} & POST & \texttt{/\allowbreak{}logout} \\ \hline
\texttt{identity-\allowbreak{}change-\allowbreak{}credentials} & POST & \texttt{/\allowbreak{}change} \\ \hline
\texttt{identity-\allowbreak{}verify} & GET & \texttt{/\allowbreak{}verify/\allowbreak{}\{token\}} \\ \hline
\end{longtable}

\section{Service Operations}
\label{sec:operations}

The interfaces of the \texttt{identity} service, its operations, data models and implementation are provided below.
In particular, each subsection first names the HTTP method and path used to call the operation, after which it names the abstract operation from the \texttt{identity} SD document, as well as input and output types.

All operations require the requester's identity, presented according to the provider's authentication policy: the client certificate (mutual TLS) and, with the \texttt{outsourced} policy, \texttt{Authorization: Bearer IDENTITY-TOKEN//<token>}; systems holding the Authentication secret key send \texttt{Bearer AUTHENTICATOR-KEY//<system>//<hash>}, and with the \texttt{declared} policy \texttt{Bearer SYSTEM//<system>} is sent. Request and response bodies are \texttt{application/json}.
Errors are answered with an \mref{ErrorMessage} body and the status codes \texttt{400 Bad Request} (invalid parameter), \texttt{401 Unauthorized} (missing or invalid identity), \texttt{403 Forbidden} (not permitted, e.g. by the management or blacklist filter), \texttt{404 Not Found}, \texttt{408 Request Timeout}, \texttt{423 Locked}, \texttt{500 Internal Server Error} and \texttt{503 Service Unavailable} (a system it depends on failed).

\osubsection{identity-login}{POST}{/\allowbreak{}authentication/\allowbreak{}identity/\allowbreak{}login}{\mref{IdentityRequest}}{\mref{IdentityLoginResponse}}

Checks the credentials and opens a session. Returns the identity token and its expiry (\texttt{identity.\allowbreak{}token.\allowbreak{}duration}, 300 s in the default configuration). A previous token of the system becomes invalid.

A successful call returns \texttt{200 OK} with the output in the body.

\begin{lstlisting}[label={lst:identity-login},caption={An \oref{identity-login} invocation.}]
POST /authentication/identity/login HTTP/1.1
Host: authentication:8444
Authorization: Bearer IDENTITY-TOKEN//<token>
Content-Type: application/json

{
  "systemName": "TemperatureSensor",
  "credentials": {
    "password": "<password>"
  }
}
\end{lstlisting}

\begin{lstlisting}[label={lst:identity-login-resp},caption={An \oref{identity-login} response.}]
{
  "token": "<token>",
  "expirationTime": "2026-10-22T12:00:00Z"
}
\end{lstlisting}

\osubsection{identity-logout}{POST}{/\allowbreak{}authentication/\allowbreak{}identity/\allowbreak{}logout}{\mref{IdentityRequest}}{}

Checks the credentials and closes the session of the system.

A successful call returns \texttt{200 OK}.

\begin{lstlisting}[label={lst:identity-logout},caption={An \oref{identity-logout} invocation.}]
POST /authentication/identity/logout HTTP/1.1
Host: authentication:8444
Authorization: Bearer IDENTITY-TOKEN//<token>
Content-Type: application/json

{
  "systemName": "TemperatureSensor",
  "credentials": {
    "password": "<password>"
  }
}
\end{lstlisting}

\osubsection{identity-change-credentials}{POST}{/\allowbreak{}authentication/\allowbreak{}identity/\allowbreak{}change}{\mref{IdentityChangeRequest}}{}

Checks the current credentials and replaces them with the new ones.

A successful call returns \texttt{200 OK}.

\begin{lstlisting}[label={lst:identity-change-credentials},caption={An \oref{identity-change-credentials} invocation.}]
POST /authentication/identity/change HTTP/1.1
Host: authentication:8444
Authorization: Bearer IDENTITY-TOKEN//<token>
Content-Type: application/json

{
  "systemName": "TemperatureSensor",
  "credentials": {
    "password": "<password>"
  },
  "newCredentials": {
    "password": "<password>"
  }
}
\end{lstlisting}

\osubsection{identity-verify}{GET}{/\allowbreak{}authentication/\allowbreak{}identity/\allowbreak{}verify/\allowbreak{}\fparam{\{token\}}}{\pref{String}}{\mref{IdentityVerifyResponse}}

Checks an identity token. Returns whether it is valid and, if so, the system, its sysop flag, login and expiry time. The caller must itself present a valid identity token (only \texttt{login}, \texttt{logout} and \texttt{change} are token-free).

Path parameter: \fparam{token}.

A successful call returns \texttt{200 OK} with the output in the body.

\begin{lstlisting}[label={lst:identity-verify},caption={An \oref{identity-verify} invocation.}]
GET /authentication/identity/verify/<token> HTTP/1.1
Host: authentication:8444
Authorization: Bearer IDENTITY-TOKEN//<token>
\end{lstlisting}

\begin{lstlisting}[label={lst:identity-verify-resp},caption={An \oref{identity-verify} response.}]
{
  "verified": true,
  "systemName": "TemperatureSensor",
  "sysop": false,
  "loginTime": "2026-10-22T12:00:00Z",
  "expirationTime": "2026-10-22T12:00:00Z"
}
\end{lstlisting}

\section{Data Models}
\label{sec:model}

Here, all data objects that can be part of the service calls associated with this service are listed in alphabetic order.
Note that each subsection, which describes one type of object, begins with the \textit{struct} keyword, which is meant to denote a JSON \pref{Object} that must contain certain fields, or names, with values conforming to explicitly named types.
Fields that are not needed may be omitted or \texttt{null} in requests; empty fields are omitted in responses.
As a complement to the primary types defined in this section, there is also a list of secondary types in Section \ref{sec:model:primitives}, which are used to represent things like hashes, identifiers and texts.

\subsection{Primitives}
\label{sec:model:primitives}

As all messages are encoded using the JSON format \cite{rfc8259}, the following primitive constructs, part of that standard, become available.
Note that the official standard is defined in terms of parsing rules, while this list only concerns syntactic information.
Furthermore, the \pref{Object} and \pref{Array} types are given optional generic type parameters, which are used in this document to signify when pair values or elements are expected to conform to certain types.

\noindent\begin{tabularx}{\textwidth}{| p{4.6cm} | X |} \hline
\rowcolor{gray!33} Type & Description \\ \hline
\pdef{Boolean} & JSON Boolean, \texttt{true} or \texttt{false}. \\ \hline
\pdef{DateTime} & JSON String with an ISO 8601 UTC timestamp, e.g. \texttt{2026-10-22T12:00:00Z}. \\ \hline
\pdef{ExceptionType} & One of \texttt{ARROWHEAD}, \texttt{INVALID\_\allowbreak{}PARAMETER}, \texttt{AUTH}, \texttt{FORBIDDEN}, \texttt{DATA\_\allowbreak{}NOT\_\allowbreak{}FOUND}, \texttt{TIMEOUT}, \texttt{LOCKED}, \texttt{INTERNAL\_\allowbreak{}SERVER\_\allowbreak{}ERROR}, \texttt{EXTERNAL\_\allowbreak{}SERVER\_\allowbreak{}ERROR} (JSON String). \\ \hline
\pdef{Number} & JSON Number, an integer. \\ \hline
\pdef{Object} & JSON Object; \pref{Object}$<$A$>$ has string keys and values of type A. \\ \hline
\pdef{String} & JSON String. \\ \hline
\end{tabularx}
