\section{Overview}
\label{sec:overview}

This document describes the \texttt{choreographer\allowbreak{}Session} service interface of the Choreographer system, which provides starting and aborting sessions of workflow plans by their clients.

It's implemented using protocol, encoding as stated in below table:
\begin{table}[ht!]
  \centering
  \begin{tabular}{|l|l|l|}
    \hline
    \rowcolor{gray!33} Profile type & Type & Version \\ \hline
    Transfer protocol & HTTP & 1.1 \cite{rfc9112} \\ \hline
    Data encryption & TLS & 1.3 \cite{rfc8446}, 1.2 \cite{rfc5246} \\ \hline
    Encoding & JSON & RFC 8259 \cite{rfc8259} \\ \hline
    Compression & N/A & - \\ \hline
    Semantics & N/A & - \\ \hline
    Ontology & N/A & - \\ \hline
  \end{tabular}
  \caption{Communication and semantics details used for the \texttt{choreographer\allowbreak{}Session} service interface}
  \label{tab:comunication_semantics_profile}
\end{table}

This document provides the Interface Design Description IDD to the \textit{choreographerSession -- Service Description} document \cite{cho-choreographerSession-sd}.
For further details about how this service is meant to be used, please consult that document.

The rest of this document describes how to realize the \texttt{choreographer\allowbreak{}Session} service
interface in detail. Both in terms of its operations (Section \ref{sec:operations}) and its information model (Section \ref{sec:model}).

\subsection{Interface registration}

The service is registered in the ServiceRegistry with the interface template \texttt{generic\_\allowbreak{}https}, policy \texttt{CERT\_\allowbreak{}AUTH}, access address \texttt{choreographer}, port 8457 (\texttt{server.\allowbreak{}port}; the standalone deployment registers 8454) and base path \texttt{/\allowbreak{}choreographer/\allowbreak{}session}. The \texttt{operations} property of the interface lists the operations below with their method and path relative to the base path (path parameters are placeholders such as \texttt{\{id\}} that the consumer fills in):

\noindent\begin{longtable}{| p{5.2cm} | p{1.6cm} | p{8.4cm} |} \hline
\rowcolor{gray!33} Operation & Method & Path \\ \hline \endhead
\texttt{start-\allowbreak{}session} & POST & \texttt{/\allowbreak{}start} \\ \hline
\texttt{abort-\allowbreak{}session} & DELETE & \texttt{/\allowbreak{}abort/\allowbreak{}\{id\}} \\ \hline
\end{longtable}

\section{Service Operations}
\label{sec:operations}

The interfaces of the \texttt{choreographer\allowbreak{}Session} service, its operations, data models and implementation are provided below.
In particular, each subsection first names the HTTP method and path used to call the operation, after which it names the abstract operation from the \texttt{choreographer\allowbreak{}Session} SD document, as well as input and output types.

All operations require the requester's identity, presented according to the provider's authentication policy: the client certificate (mutual TLS) and, with the \texttt{outsourced} policy, \texttt{Authorization: Bearer IDENTITY-TOKEN//<token>}; systems holding the Authentication secret key send \texttt{Bearer AUTHENTICATOR-KEY//<system>//<hash>}, and with the \texttt{declared} policy \texttt{Bearer SYSTEM//<system>} is sent. Request and response bodies are \texttt{application/json} unless stated otherwise.
Errors are answered with an \mref{ErrorMessage} body and the status codes \texttt{400 Bad Request} (invalid parameter), \texttt{401 Unauthorized} (missing or invalid identity), \texttt{403 Forbidden} (not permitted, e.g. by the management, authorization or blacklist filter), \texttt{404 Not Found}, \texttt{408 Request Timeout}, \texttt{423 Locked}, \texttt{500 Internal Server Error} and \texttt{503 Service Unavailable} (a system it depends on failed).

\osubsection{start-session}{POST}{/\allowbreak{}choreographer/\allowbreak{}session/\allowbreak{}start}{\mref{StartSessionListRequest}}{\mref{RunPlanListResponse}}

Starts sessions of plans by name for the requester.

A successful call returns \texttt{201 Created} with the output in the body.

\begin{lstlisting}[label={lst:start-session},caption={An \oref{start-session} invocation.}]
POST /choreographer/session/start HTTP/1.1
Host: choreographer:8457
Authorization: Bearer IDENTITY-TOKEN//<token>
Content-Type: application/json

{
  "sessions": [
    {
      "planName": "fillTank",
      "quantity": 1,
      "allowInterCloud": true,
      "chooseOptimalExecutor": true,
      "notifyProtocol": "HTTPS",
      "notifyAddress": "192.168.0.20",
      "notifyPort": 8080,
      "notifyPath": "/notify"
    }
  ]
}
\end{lstlisting}

\begin{lstlisting}[label={lst:start-session-resp},caption={An \oref{start-session} response.}]
{
  "entries": [
    {
      "planId": 1,
      "sessionId": 1,
      "quantity": 1,
      "status": "INITIATED",
      "errorMessages": [
        "string"
      ],
      "needInterCloud": true
    }
  ]
}
\end{lstlisting}

\osubsection{abort-session}{DELETE}{/\allowbreak{}choreographer/\allowbreak{}session/\allowbreak{}abort/\allowbreak{}\fparam{\{id\}}}{\pref{String}}{}

Aborts a session owned by the requester.

Path parameter: \fparam{id}.

A successful call returns \texttt{200 OK}.

\begin{lstlisting}[label={lst:abort-session},caption={An \oref{abort-session} invocation.}]
DELETE /choreographer/session/abort/<id> HTTP/1.1
Host: choreographer:8457
Authorization: Bearer IDENTITY-TOKEN//<token>
\end{lstlisting}

\section{Data Models}
\label{sec:model}

Here, all data objects that can be part of the service calls associated with this service are listed in alphabetic order.
Note that each subsection, which describes one type of object, begins with the \textit{struct} keyword, which is meant to denote a JSON \pref{Object} that must contain certain fields, or names, with values conforming to explicitly named types.
Fields that are not needed may be omitted or \texttt{null} in requests; empty fields are omitted in responses.
As a complement to the primary types defined in this section, there is also a list of secondary types in Section \ref{sec:model:primitives}, which are used to represent things like hashes, identifiers and texts.

\subsection{Primitives}
\label{sec:model:primitives}

As all messages are encoded using the JSON format \cite{rfc8259}, the following primitive constructs, part of that standard, become available.
Note that the official standard is defined in terms of parsing rules, while this list only concerns syntactic information.
Furthermore, the \pref{Object} and \pref{Array} types are given optional generic type parameters, which are used in this document to signify when pair values or elements are expected to conform to certain types.

\noindent\begin{tabularx}{\textwidth}{| p{4.6cm} | X |} \hline
\rowcolor{gray!33} Type & Description \\ \hline
\pdef{Array} & A JSON Array \cite{rfc8259}; \pref{Array}$<$A$>$ has elements of type A. \\ \hline
\pdef{Boolean} & JSON Boolean, \texttt{true} or \texttt{false}. \\ \hline
\pdef{ExceptionType} & One of \texttt{ARROWHEAD}, \texttt{INVALID\_\allowbreak{}PARAMETER}, \texttt{AUTH}, \texttt{FORBIDDEN}, \texttt{DATA\_\allowbreak{}NOT\_\allowbreak{}FOUND}, \texttt{TIMEOUT}, \texttt{LOCKED}, \texttt{INTERNAL\_\allowbreak{}SERVER\_\allowbreak{}ERROR}, \texttt{EXTERNAL\_\allowbreak{}SERVER\_\allowbreak{}ERROR} (JSON String). \\ \hline
\pdef{Number} & JSON Number, an integer. \\ \hline
\pdef{Object} & JSON Object; \pref{Object}$<$A$>$ has string keys and values of type A. \\ \hline
\pdef{SessionStatus} & One of \texttt{INITIATED}, \texttt{RUNNING}, \texttt{ABORTED}, \texttt{DONE} (JSON String). \\ \hline
\pdef{String} & JSON String. \\ \hline
\end{tabularx}
