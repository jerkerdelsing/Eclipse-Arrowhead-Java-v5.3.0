\section{Overview}
\label{sec:overview}

This document describes the \texttt{blacklistDiscovery} service, which provides checking whether a system is blacklisted in the local cloud, and listing the requester's own active entries.
It is produced by the Blacklist system \cite{bl-sysd} in service version 1.0.0.

The rest of this document is organized as follows.
In Section \ref{sec:operations}, we describe the abstract message operations provided by the service.
In Section \ref{sec:model}, we end the document by presenting the data types used by the mentioned operations.
The concrete interfaces are specified in the HTTP/TLS/JSON IDD \cite{bl-blacklistDiscovery-http-idd} and the MQTT/TLS/JSON IDD \cite{bl-blacklistDiscovery-mqtt-idd}.

\subsection{Significant Prior Art}

Blacklist is new in Arrowhead 5; in 4.x systems were excluded only by removing their certificates or authorization rules.

\subsection{How This Service Is Meant to Be Used}

The blacklist filter of the common library calls \texttt{check} for every request it receives when \texttt{enable.\allowbreak{}blacklist.\allowbreak{}filter=\allowbreak{}true}; Dynamic\allowbreak{}Service\allowbreak{}Orchestration uses the Blacklist to remove blacklisted candidates. A system can call \texttt{lookup} to see the entries about itself.

\subsection{Important Delimitations and Dependencies}
\label{sec:delimitations}

The service only answers; enforcement is done by the systems' blacklist filters. With \texttt{force.\allowbreak{}blacklist.\allowbreak{}filter=\allowbreak{}true} a system refuses requests while the Blacklist is unreachable. Core systems in \texttt{blacklist.\allowbreak{}check.\allowbreak{}exclude.\allowbreak{}list} are not checked.

\section{Service Interface}
\label{sec:operations}

This section describes the interfaces to the \texttt{blacklistDiscovery} service.
In particular, each subsection names an abstract operation, an input type and an output type, in that order.
The input type is named inside parentheses, while the output type is preceded by a colon.
Input and output types are only denoted when accepted or returned, respectively, by the interface in question.

All abstract data types named in this section are defined in Section \ref{sec:model}.

The following interface operations are available.

\osubsection{check}{\pref{Name}}{\pref{Boolean}}

Returns true if the named system has an active blacklist entry. The system name fills the \texttt{\{systemName\}} placeholder of the registered path.

\osubsection{lookup}{}{\mref[Blacklist\allowbreak{}Entry\allowbreak{}List\allowbreak{}Response]{BlacklistEntryListResponse}}

Returns the active entries about the requester.

\section{Information Model}

Here, all data objects that can be part of the \texttt{blacklistDiscovery} service are listed in alphabetic order.
Note that each subsection, which describes one type of object, begins with the \textit{struct} keyword, which is used to denote a collection of named fields, each with its own data type.
As a complement to the explicitly defined types in this section, there is also a list of implicit primitive types in Section \ref{sec:model:primitives}, which are used to represent things like hashes and identifiers.
