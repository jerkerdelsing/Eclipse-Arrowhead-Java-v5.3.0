This is the 5.3.0 documentation edition, dated 2026-11-09. It carries forward the system and service contracts from the retained 5.2.2 documentation and identifies the current primary implementation sources. The former \path|documentation/v5.2.2| folder is retained unchanged.

Document version 5.3.0 is distinct from executable, dependency, registered system/service and wire-contract versions. \section{Overview}
\label{sec:overview}

This document describes the \texttt{blacklist\allowbreak{}Management} service interface of the Blacklist system over MQTT, which provides operator management of the blacklist: adding systems with a reason and expiry, querying entries and inactivating them.

It's implemented using protocol, encoding as stated in below table:
\begin{table}[ht!]
  \centering
  \begin{tabular}{|l|l|l|}
    \hline
    \rowcolor{gray!33} Profile type & Type & Version \\ \hline
    Transfer protocol & MQTT & 3.1.1 \cite{mqtt311} \\ \hline
    Data encryption & TLS & 1.3 \cite{rfc8446}, 1.2 \cite{rfc5246} \\ \hline
    Encoding & JSON & RFC 8259 \cite{rfc8259} \\ \hline
    Compression & N/A & - \\ \hline
    Semantics & N/A & - \\ \hline
    Ontology & N/A & - \\ \hline
  \end{tabular}
  \caption{Communication and semantics details used for the \texttt{blacklist\allowbreak{}Management} service interface}
  \label{tab:comunication_semantics_profile}
\end{table}

This document provides the Interface Design Description IDD to the \textit{blacklistManagement -- Service Description} document \cite{bl-blacklistManagement-sd}.
The operations, their semantics and the data models are the same as in the HTTP/TLS/JSON IDD \cite{bl-blacklistManagement-http-idd}; this document specifies the MQTT binding.

The MQTT interface is offered only when the system runs with \texttt{mqtt.api.enabled=true}; it is then registered with the interface template \texttt{generic\_\allowbreak{}mqtts} (\texttt{generic\_\allowbreak{}mqtt} without TLS), the broker address and port (\texttt{mqtt.\allowbreak{}broker.\allowbreak{}address}, \texttt{mqtt.\allowbreak{}broker.\allowbreak{}port}) and the base topic \texttt{arrowhead/\allowbreak{}blacklist/\allowbreak{}management/\allowbreak{}}. The standalone deployment sets \texttt{mqtt.\allowbreak{}api.\allowbreak{}enabled=\allowbreak{}false}, so the MQTT interfaces are not registered there.

\section{Service Operations}
\label{sec:operations}

The provider subscribes to one topic per operation, the base topic followed by the operation name:

\noindent\begin{longtable}{| p{5cm} | p{10.4cm} |} \hline
\rowcolor{gray!33} Operation & Request topic \\ \hline \endhead
\texttt{create} & \texttt{arrowhead/\allowbreak{}blacklist/\allowbreak{}management/\allowbreak{}create} \\ \hline
\texttt{query} & \texttt{arrowhead/\allowbreak{}blacklist/\allowbreak{}management/\allowbreak{}query} \\ \hline
\texttt{remove} & \texttt{arrowhead/\allowbreak{}blacklist/\allowbreak{}management/\allowbreak{}remove} \\ \hline
\end{longtable}

A consumer publishes a request envelope (\mref{MqttRequestTemplate}) to the topic and receives the answer (\mref{MqttResponseTemplate}) on its own \texttt{responseTopic}. The \texttt{authentication} field carries the requester's identity according to the provider's authentication policy: \texttt{IDENTITY-TOKEN//<token>} (outsourced or internal policy), \texttt{SYSTEM//<name>} (declared policy) or the requester's X.509 certificate (certificate policy). The \texttt{status} of the response uses the HTTP status code numbers (200, 201, 204, 400, 401, 403, 404, 408, 423, 500, 503); on error the payload is an \mref{ErrorMessage}.

\begin{lstlisting}[caption={Request envelope.}]
{
  "traceId": "a1b2c3",
  "authentication": "IDENTITY-TOKEN//<token>",
  "responseTopic": "arrowhead/response/TemperatureDisplay/a1b2c3",
  "qosRequirement": 1,
  "params": {},
  "payload": {}
}
\end{lstlisting}

\begin{lstlisting}[caption={Response envelope.}]
{
  "status": 200,
  "traceId": "a1b2c3",
  "receiver": "TemperatureDisplay",
  "payload": {}
}
\end{lstlisting}

\section{Go and Rust implementation variants}
\subsection{Go implementation}
Primary system folder: \path|Eclipse-Arrowhead-go/ah5-Blacklist-go|.\par
The system owns its Go module, launcher and build configuration. Use the per-system \path|Makefile| and \path|go.mod|; the containing Go tree is the build source, not a historical Arrowhead copy. Ordinary native roles use independent identities and JSON snapshot state rather than the Java database. Do not assume Java SQL migration, clustering or identical transaction/retry semantics. The registry has its own configuration and optional native AMQP monitor; other roles must be checked against their own registrations.
\paragraph{Listening port.} Built-in default 127.0.0.1:8464 (Arrowhead default). The shipped config.json, compose.yaml and Dockerfile use the same port on all interfaces ("listen": "0.0.0.0:8464"; 8540--8555 layout before 2026-11-09). Override with "listen" in the configuration file, SERVER\_PORT=N or -server.port N; the port overrides keep the configured host.
\paragraph{Native behavior and outstanding work.} Create/query/revoke, active-time checks, lookup. Golden tests for normalization, historical reactivation and query-mode edge cases. These are the boundaries recorded by the native compatibility document; later implementation changes still require direct qualification.
Native design/route evidence: \path|Eclipse-Arrowhead-go/ah5-Blacklist-go/documentation/Blacklist|.\par
For this Java interface, select only a native transport and operation explicitly implemented and advertised by that port. A matching method/path does not establish DTO, error, authorization, retry or persistence equivalence. Java MQTT/AMQP bindings are not automatically provided by a Go or Rust role. Differential contract and security checks remain necessary before substitution.
\subsection{Rust implementation}
Primary system folder: \path|Eclipse-Arrowhead-rust/ah5-Blacklist-rust|.\par
The per-system entry point is declared as a binary of \path|arrowhead-support-rust| in \path|ah5-support-runtime-rust/Cargo.toml|. Build from the primary Rust workspace with the applicable package/binary selection. Documentation links can resolve into the shared core/support catalogue. Independent process identity and state remain required.\par
The ordinary native profile uses Tokio/Axum and rustls with peer-identity checks and independent locked JSON state. Network effects are not distributed database transactions. The precise trust, CRL reload and persistence guarantees are those of the native profile, not the Java implementation.\par
\paragraph{Listening port.} Default 127.0.0.1:8464 (Arrowhead default, role blacklist). Override with "listen": "host:port" in the configuration, SERVER\_PORT=N or --server.port N; the port overrides keep the configured host.
\paragraph{Native behavior and outstanding work.} Create/revoke, expiry/check/lookup, filtered queries. Full normalization and historical query parity. These are the boundaries recorded by the native compatibility document; later implementation changes still require direct qualification.
Native design/route evidence: \path|Eclipse-Arrowhead-rust/ah5-support-runtime-rust/documentation/Blacklist|.\par
For this Java interface, select only a native transport and operation explicitly implemented and advertised by that port. A matching method/path does not establish DTO, error, authorization, retry or persistence equivalence. Java MQTT/AMQP bindings are not automatically provided by a Go or Rust role. Differential contract and security checks remain necessary before substitution.
