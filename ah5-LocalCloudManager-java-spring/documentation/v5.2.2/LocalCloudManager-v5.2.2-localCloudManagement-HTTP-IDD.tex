\section{Overview}
\label{sec:overview}

This document describes the \texttt{local\allowbreak{}Cloud\allowbreak{}Management} service interface of the LocalCloudManager system, which provides the operator console API of the local cloud: overview, registry and data views, orchestration rules, consumers, inter-cloud state, sysMonitor history and subscriptions, plant descriptions, logs and container lifecycle.

It's implemented using protocol, encoding as stated in below table:
\begin{table}[ht!]
  \centering
  \begin{tabular}{|l|l|l|}
    \hline
    \rowcolor{gray!33} Profile type & Type & Version \\ \hline
    Transfer protocol & HTTP & 1.1 \cite{rfc9112} \\ \hline
    Data encryption & TLS & 1.3 \cite{rfc8446}, 1.2 \cite{rfc5246} \\ \hline
    Encoding & JSON & RFC 8259 \cite{rfc8259} \\ \hline
    Compression & N/A & - \\ \hline
    Semantics & N/A & - \\ \hline
    Ontology & N/A & - \\ \hline
  \end{tabular}
  \caption{Communication and semantics details used for the \texttt{local\allowbreak{}Cloud\allowbreak{}Management} service interface}
  \label{tab:comunication_semantics_profile}
\end{table}

This document provides the Interface Design Description IDD to the \textit{localCloudManagement -- Service Description} document \cite{lcm-localCloudManagement-sd}.
For further details about how this service is meant to be used, please consult that document.

The rest of this document describes how to realize the \texttt{local\allowbreak{}Cloud\allowbreak{}Management} service
interface in detail. Both in terms of its operations (Section \ref{sec:operations}) and its information model (Section \ref{sec:model}).

\subsection{Interface registration}

\section{Service Operations}
\label{sec:operations}

The interfaces of the \texttt{local\allowbreak{}Cloud\allowbreak{}Management} service, its operations, data models and implementation are provided below.
In particular, each subsection first names the HTTP method and path used to call the operation, after which it names the abstract operation from the \texttt{local\allowbreak{}Cloud\allowbreak{}Management} SD document, as well as input and output types.

Requests need the console session cookie (from \texttt{login}), an allowed \texttt{Host}/\texttt{Origin}, and for \texttt{POST}, \texttt{PUT}, \texttt{PATCH} and \texttt{DELETE} the header \texttt{X-Arrowhead-Action: confirm}. Request and response bodies are \texttt{application/json} unless stated otherwise.
Errors are answered with \texttt{\{\"error\": \"<text>\"\}} and the status codes \texttt{400 Bad Request} (invalid input), \texttt{401 Unauthorized} (no valid identity or session), \texttt{403 Forbidden} (caller not permitted, request not forwarded by the console's nginx, or host/origin not allowed), \texttt{405 Method Not Allowed}, \texttt{409 Conflict} (stored entry changed since it was read), \texttt{415 Unsupported Media Type} (login without JSON), \texttt{404 Not Found}, \texttt{428 Precondition Required} (no confirmation header), \texttt{429 Too Many Requests} (login locked), \texttt{500 Internal Server Error}, \texttt{502 Bad Gateway} (a system it depends on failed) and \texttt{503 Service Unavailable} (overloaded, console password not configured, or a provider not registered).

\section{Data Models}
\label{sec:model}

Here, all data objects that can be part of the service calls associated with this service are listed in alphabetic order.
Note that each subsection, which describes one type of object, begins with the \textit{struct} keyword, which is meant to denote a JSON \pref{Object} that must contain certain fields, or names, with values conforming to explicitly named types.
Fields that are not needed may be omitted or \texttt{null} in requests; empty fields are omitted in responses.
As a complement to the primary types defined in this section, there is also a list of secondary types in Section \ref{sec:model:primitives}, which are used to represent things like hashes, identifiers and texts.

\subsection{Primitives}

Note that the official standard is defined in terms of parsing rules, while this list only concerns syntactic information.
Furthermore, the \pref{Object} and \pref{Array} types are given optional generic type parameters, which are used in this document to signify when pair values or elements are expected to conform to certain types.

\noindent\begin{tabularx}{\textwidth}{| p{4.6cm} | X |} \hline
\rowcolor{gray!33} Type & Description \\ \hline
\pdef{Array} & A JSON Array \cite{rfc8259}; \pref{Array}$<$A$>$ has elements of type A. \\ \hline
\pdef{Boolean} & JSON Boolean, \texttt{true} or \texttt{false}. \\ \hline
\pdef{DateTime} & JSON String with an ISO 8601 UTC timestamp, e.g. \texttt{2026-10-22T12:00:00Z}. \\ \hline
\pdef{Number} & JSON Number, an integer. \\ \hline
\pdef{Object} & JSON Object; \pref{Object}$<$A$>$ has string keys and values of type A. \\ \hline
\pdef{String} & JSON String. \\ \hline
